# Composer/media, room mention, scheduled send, fresh hydration (#1123, #1124, #1125, #1130)

Four independent defect fixes collected into one deliverable at the maintainer's
request. Each keeps the existing layer ownership: Rust owns product state and
Matrix semantics, React renders Rust DTOs and dispatches typed commands.

## #1123 — `@room` is never a pill in the timeline

Element sends the spec-standard room mention as `{"body": "@room ",
"m.mentions": {"room": true}, "msgtype": "m.text"}`. Element's own pillifier
scans **text nodes** for room notifications, so a formatted body needs no anchor
either.

Design:

- Add `mentions_room: bool` to `koushi_protocol::event::timeline::TimelineItem`,
  projected by `mentions_room_from_event_json`, which reuses the existing
  `mention_intent_from_event_json` reader (the same reader behind
  `mentioned_user_ids_from_event_json`). Reusing it keeps the room flag on the
  same `m.mentions` and edit-effective-content rules, including `m.new_content`,
  with no second raw-event parser. Set in the room item projection and the
  thread projection, so a room-mention event renders the same way in the main
  timeline and inside a thread.
- Thread the mention facts through `renderPlainTextBody`/`renderTimelineMessageText`
  in `TimelineMessageBody.tsx` as one `TimelineMentionFacts` value (`userIds` +
  `room`) instead of a bare user-id set. The mention token list gains a
  discriminated `{ kind: "room", token: "@room" }` entry next to the user tokens,
  so the pill element is shared and only the DOM attribute differs: room pills
  carry `data-mention-room="true"` instead of `data-mention-user-id`, and reuse
  the existing `.message-mention-pill` style.
- The formatted renderer keeps its existing rule: user mentions are recognized
  through their `matrix.to` anchors and nothing else. A room token inside a
  formatted body is therefore not pilled. Pilling formatted text nodes would have
  to resolve mention boundaries across sibling elements (`x<strong>@room</strong>y`
  renders as `x@roomy`) and would otherwise pill `@room` inside inline code and
  link labels; the reported Element event carries no `formatted_body`, so the
  plain renderer is where the defect lives.
- No new CSS, no new component, no client-side inference of `m.mentions`.

Boundary the fix deliberately keeps: the token only pills when `@room` stands on
a mention boundary, so a Koushi-sent `@@room` body (the doubled at-sign of
#1122, a separate composer defect) is unchanged.

## #1124 — Linux: the scheduled send time cannot be changed

Not fixed: the reported failure could not be established, so the diagnostics are
recorded here instead of turning into a speculative control replacement.

Run on the committed Linux GUI lane (WebKitGTK under Xvfb, the committed
`docker/linux-gui.Dockerfile` image, scenario `local-scheduled-send`,
`--server=tuwunel`), with a diagnostic that drives the field the way a human does
rather than through the lane's own value setter:

- The scheduled-send field is a real native control on this WebKitGTK and a human
  can edit it with the keyboard. Focusing it and pressing `ArrowUp` twice moved
  the focused segment a month forward, and typing a digit set it; the field stayed
  `type=datetime-local`, valid, writable and enabled. Recorded output:
  `gui_local_scheduled_input_probe={"before":{"found":true,"readOnly":false,"disabled":false,"type":"datetime-local","value":"2026-10-05T21:15","valid":true},"afterArrows":{"value":"2026-11-05T21:15"},"afterTyping":{"value":"2026-03-05T21:15"}}`.
- The native calendar popup is a GTK UI-process window, not DOM, so neither the
  lane's value setter nor WebDriver can drive it. That path stays unverified here.
- The lane's reschedule step could not pass at all: it looked for a button whose
  visible text starts with `Save scheduled send`, while that string is only the
  button's accessible name and its visible text is `Save`. The edit path had
  therefore never been exercised. Now matched by accessible name.
- A short-fuse schedule (now + 45 s) is created and then fires: the lane now
  waits for the fired event row and reports `gui_local_scheduled_fire=ok`, which
  it never did before.

Conclusion: on the committed Linux environment, create, edit, cancel and fire all
work and the time field is keyboard-editable, so the reported failure is not
reproducible there. Changing the control needs the reporter's distribution and
WebKitGTK version; if the native picker turns out to be the cause, replacing it
with an app-rendered date/time control is the next step.

Running the Linux lane from an Apple Silicon host also needed three environment
fixes, one of which is a repository bug worth keeping: the NSS-wrapper library
path was hard-coded to `/usr/lib/x86_64-linux-gnu`, which silently disables the
wrapper on an arm64 image and makes the lane fail to start DBus. The lookup now
accepts either architecture. The other two are Docker-invocation details (a
case-sensitive volume for the Cargo target directory, and a writable
`RUSTUP_HOME`), not repository changes.

## #1125 — a fresh room subscription loses the message behind hidden state

`should_hydrate_empty_initial_room_timeline` correctly detects a projection with
no displayed row (#1110), but the hydration that followed was a single bounded
`paginate_backwards(INITIAL_EMPTY_ROOM_BACKFILL_EVENT_COUNT)` pass. When more
hidden state events than that window precede the message, a fresh subscription's
window was still all-hidden and the reader got an empty conversation.

Design:

- Keep the bounded trigger and the account-work admission per pass; make the
  *outcome* of a pass feed the decision again. After re-subscribing and
  re-projecting, repeat the guarded backward pass while the projection still has
  no displayed row, up to `INITIAL_EMPTY_ROOM_HYDRATION_MAX_ROUNDS` (8).
- Stop on a projection with a displayed row, a pass that reports the start of the
  timeline was reached, an error, or the round cap. The cap is the bound rather
  than a "the window edges did not move" check: a fetched page can reach the
  timeline after its pagination call returns, so an edge comparison would stop
  one pass too early and silently under-hydrate again. Each round re-uses the
  existing pagination trace points, so a capped hydration is diagnosable.
- The previously ignored test
  `crates/koushi-core/src/timeline/actor/fresh_room_hydration_tests.rs::
  fresh_room_subscription_reaches_a_message_behind_hidden_state_events` is now
  the regression guard.

Evidence: RED with the single pass (`items=120, hidden=120`, message absent),
GREEN after the loop (`count=128`, message present).

Known ceiling: a live edge with more than eight windows of hidden state events
still carries no displayed row after hydration; the trace records the capped
round count instead of paginating without end.

## #1130 — sending staged attachments wipes the typed composer draft

`sendStagedAttachmentsInner` ended with `AcceptComposerDraft`, which deletes the
room's composer draft, while the send itself only ever read the staged items'
own captions. Typed text was destroyed without being sent.

Design: the staged-attachment send settles the composer draft without consuming
it.

- `AppCommand::AcceptComposerDraft` and `AppAction::ComposerDraftAccepted` gain
  `consumes_draft`. A staged-attachment send passes `false`:
  `ComposerDraftStore::settle_room_revision` / `settle_thread_revision` advance
  the revision (and the LRU/tombstone accounting) exactly like an accepted send
  while leaving the draft document in place. The consuming paths — plain, reply,
  thread reply and scheduled sends — are unchanged.
- Accepting at all is deliberate: the acceptance is also what performs the #1037
  return-to-live transition (`return_main_pane_to_live_for_accepted_send`), which
  an attachment send needs exactly as a text send does. Dropping the acceptance
  entirely would have anchored the main pane after every attachment send, which
  is what the first draft of this change did.
- The renderer needs no acceptance back: the Tauri command answers with the plain
  command settlement, so React does not clear its local composer overlay. The
  staged-attachment call sites still capture and pass the draft revision, because
  the send still settles it, but nothing in the renderer consumes the accepted
  revision any more.
- The text path is untouched: with text in the composer, Enter still sends the
  text and leaves the staged items staged.

Not taken here: adopting the composer text as the sent item's caption. It is
attractive (one event, no text/image split) but it changes the documented
per-item caption ownership (`docs/agents/state-ownership.md`, "Media") and would
require Core to publish the adopted caption into staging state before enqueue,
plus a consumed-versus-preserved signal for the renderer's revision bookkeeping.
That is its own change; the mandatory half of #1130 — never silently wiping an
unsent draft — is what this PR fixes.

## Independent pre-review (gpt-6.1-sol), and what changed because of it

- BLOCKER: "no frontend change" for #1130 was wrong (the reserved accepted
  revision would skew the next send). Fixed by removing the reservation and the
  acceptance together, as the review's smallest alternative suggested.
- BLOCKER: implicit caption adoption contradicts the documented per-item caption
  ownership and would leave the staging tray showing a different caption than the
  payload. The bridge was dropped from this PR (see above).
- IMPORTANT: adoption could also race the debounced draft persistence. Dropped
  with the bridge.
- IMPORTANT: `paginate_backwards`'s `false` does not mean "no progress", so a
  round cap alone was not a bound. The loop now also stops when a pass does not
  move the window edges.
- IMPORTANT: the thread and room projections do not read the same `raw` for
  edits. Both now read the shared mention-intent reader; the remaining
  difference is in the input each caller passes, not in the new reader.
- IMPORTANT: the Linux lane cannot diagnose human editability. Recorded above
  instead of claiming a cause.

## Independent post-review (gpt-6.1-sol), and what changed because of it

- IMPORTANT: dropping `AcceptComposerDraft` had also dropped the #1037
  return-to-live transition for attachment sends. Fixed with `consumes_draft`,
  which keeps the acceptance (and therefore the guarded navigation transition)
  while preserving the draft content. The state-level test
  `accepted_attachment_send_settles_the_draft_without_clearing_it` now covers the
  preserved path next to the existing navigation assertions.
- IMPORTANT: pilling formatted text nodes could mis-pill across siblings and
  inside inline code or link labels. The formatted renderer keeps its previous
  rule and only the plain renderer draws room pills; recorded above.
- IMPORTANT: the hydration loop's "edges did not move" stop could fire before an
  asynchronously delivered page reached the timeline. The loop is now bounded by
  the round cap alone.
- IMPORTANT: the lane's reschedule assertion only proved the section still
  existed. It now reopens the edited row and waits for the Rust-projected time to
  equal the value it submitted.
- MINOR: the short-fuse schedule could land in the past because the shared
  value formatter truncates seconds. The fuse is now 90 s.
- Not changed, with reason: `mentions_room` is absent on local echoes and on
  synthetic pending-send projections exactly as `mentioned_user_ids` is, so a
  just-sent room mention pills only once its echo arrives — the same inherited
  gap user mentions have. A fetched thread root also reads the original payload
  for both fields, so an edited-away mention behaves identically for both; that
  is a pre-existing root-projection limitation, not a new one.
- Delete list: the redundant outer `if` around the hydration loop was rejected
  as a coin flip that only costs a re-check of the same predicate; the
  `accountOwner` guard in the two attachment call sites was kept because it is an
  existing validity check on the captured account, not correlation bookkeeping.
