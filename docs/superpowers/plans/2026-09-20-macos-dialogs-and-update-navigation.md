# macOSのダイアログ配置とアップデート導線の統一

状態: 実装・独立レビュー・ローカル検証完了。[PR #951](https://github.com/shinaoka/koushi-matrix/pull/951) のCIとマージ確認までを対象とする。
調査基点: `origin/main` / `2dc51dd17ebc7e1749f24ddacf58d8f6bce4f32e`。

2026-09-20追記: ユーザー指定により、標準ボタンの保持と上部安全領域の方針を
[`REPOSITORY_RULES.md`](../../../REPOSITORY_RULES.md#macos-native-window-controls-and-overlay-layout)
に規範として追加した。以下の調査記録は実装前の状態であり、検証結果は末尾に追記する。

## 目的とユーザー指定

- macOSの赤・黄・緑の標準ウィンドウボタンに、設定などの内容が重ならない。
- 過去に採用した「標準ボタンを残して上部に余白を取る」方針を全対象画面に適用する。
- `Koushi → アップデートを確認…` から直接チェック結果と更新操作に進める。
- アップデートを `User settings → Preferences → Display` に埋め込む導線を解消する。
- まず計画を作成し、その後の明示的な承認に基づき修正・PR作成・マージまで対応する。
  アプリの配布、リリース、インストール済みアプリの置換は今回の対象外。

## 調査で確認した事実

### 過去の修正が引き継がれなかった経緯

`f1e1b20a`（2026-09-12、添付プレビュー修正）は、添付ステージング、原寸プレビュー、
タイムライン画像ビューアにmacOSの上部安全領域を導入した。
`docs/worklogs/2026-09-12-attachment-fit-modal.md` の Native titlebar follow-up に、
ユーザーが上部余白を選択したことと、Chromium/WebKitで検証したことが記録されている。

その後の `4e298c79`（同日、設定のモーダル化）は新しい `ModalDialog` / `.app-modal`
を追加したが、安全領域を使わなかった。両コミットは調査基点の祖先である。
したがって、既存の方針を新しい共通部品へ反映しなかった適用漏れである。
Windowsのタイトルバー問題という以前の説明は誤り。

### 対象の棚卸し

下表の「未適用」はソース上の確認であり、各画面での実機再現を済ませたという意味ではない。
実装前に対象ごとのDOM配置テストで再現条件を確定する。

| 系統 | 対象と現状 | 対応方針 |
| --- | --- | --- |
| `ModalDialog` / `.app-modal` | 設定、ヘルプ、ローカルデータリセットなどの確認。上部安全領域は未適用 | 共通モーダルで配置・最大高さを保証 |
| `.dialog-overlay` / `.dialog-box` | ルーム/Space作成、ユーザーID入力、招待、通報、診断、画像圧縮、ディレクトリのプレビュー。上部安全領域は未適用 | 共通モーダルへ統合。本文スクロールと操作ボタンの到達性を維持 |
| 子ダイアログ | 暗号鍵入出力のパスフレーズ、Spaceメンバーの権限変更確認。独自overlayを使用 | 親の上に開く共通モーダルへ統合し、閉じる順序とフォーカス復帰を保証 |
| `.media-viewer-backdrop` | メディア一覧から開くビューア。通常の24px余白のみ | 共通の安全領域と利用可能高さを適用 |
| 既存の安全領域対応画面 | 添付ステージング、原寸プレビュー、タイムライン画像ビューア | 共通契約へ接続。余白の二重加算を防ぐ |
| `floatingLayer.tsx` | 絵文字、既読者、各種メニュー等。通常viewportの16px境界のみ | 安全領域と呼び出し元境界の積集合で配置。モーダル内からの表示は親のtop layerも考慮 |
| その他の独自表示 | メッセージソース、接続状態、TrustHelp、セッション検証のインライン確認 | モーダル・ポップオーバー・インラインを区別して監査。インライン表示に窓全体の余白を重複適用しない |

安全領域は現在 `:root:has(.titlebar[data-platform="macos"])` に依存している。
ログイン前や復旧画面でタイトルバーDOMが存在しない場合、同じMacでもこの条件が成立しない。
この依存も共通化の対象とする。

### 更新機能の導線

- ネイティブの更新確認は現在Helpメニューにある。
- `App.tsx` の `checkForUpdates` は設定全体を開いてからチェックする。
  設定はAccountカテゴリで開くため、チェック結果があるPreferencesまで直接到達しない。
- 更新コントロールは `UserSettingsPanel.tsx` のDisplay内にあり、macOSだけに表示される。
- 新版検出時には別経路でOSの確認ダイアログも出る。更新結果の表示先と確認操作が分散している。
- 更新設定とチェック/ダウンロード/インストール状態の所有者はRust/Tauri。
  自動チェックの初期値は有効、起動時と24時間間隔。自動インストールとは異なる。

## 統一後の導線

| 操作 | 入口 | 表示先・動作 |
| --- | --- | --- |
| 設定を開く | `Koushi → 設定…`、`Cmd+,`、サイドバーの設定 | 同じ設定ダイアログ。同じラベル体系と開閉動作 |
| 更新を確認する | `Koushi → アップデートを確認…` | 専用の更新ダイアログを直接開いてチェック。設定カテゴリの移動は不要 |
| 自動チェック・プレリリースの設定 | 同じ更新ダイアログ | Rustの既存設定を表示・変更。Displayから移動し、新しい設定カテゴリは増やさない |
| 自動チェックで新版を検出 | 既存のRust更新イベント | 同じ更新ダイアログに新版とダウンロード操作を表示。別の確認画面を重ねない |
| 更新を適用する | 同じ更新ダイアログ | 明示的にダウンロードし、検証完了後に「再起動してインストール」。自動で再起動しない |
| ヘルプ・アプリ情報 | Helpメニュー／KoushiのAbout | 現在の用途を維持。更新確認の入口をHelpには重複して置かない |

更新ダイアログはアカウントや右ペインから独立したアプリ全体の表示とし、ログイン前・
検証待ちにも到達できるようにする。手動チェックのためにMatrixのスレッド等を閉じない。
すでに更新ダイアログが開いているときの再選択は既存の画面を前面に出し、複製しない。
チェック中・ダウンロード中・インストール準備済み等の重複処理は既存のRustガードに従う。
確認中、最新版、取得可能、ダウンロード中、再起動待ち、失敗、未対応を明示する。
署名鍵のない開発ビルドなども空白画面にしない。

表示名は英語/Japaneseのカタログへ揃える。既存の設定値、既定値、更新チャンネル、
署名検証、更新周期は変更しない。Windows/Linuxへの更新機能拡張は今回の対象外。

## 共通の配置・操作契約

1. **安全領域を一箇所で決める。** Rustが解決したplatformと既存のネイティブ窓情報を
   アプリルートへ反映し、タイトルバーDOMの有無から切り離す。macOSでは既存の44pxを
   起点に評価し、非macOSには不要な余白を追加しない。WebViewズームとネイティブ座標の
   違いは実機で検証し、固定CSS値で不足する場合はアダプターで換算する。
2. **共通モーダルが安全領域内の配置・最大高さ・スクロールを所有する。** 個々の機能は
   タイトル、本文、操作、閉じる可否を渡す。背景の暗幕は窓を覆ってよいが、内容と操作は
   標準ボタンの下に収まる。小窓・拡大時も閉じる/キャンセル/確定へ到達できる。
3. **モーダルとポップオーバーを区別する。** モーダルはbrowser top layerとfocus containmentを
   使用。ポップオーバーは共通の配置計算を使用し、親モーダルの背後やinertなbodyに出さない。
   パネル内のインライン確認には、役割に合う表示とアクセシビリティ属性を与える。
4. **開閉を揃える。** Escapeは最前面の閉じられる画面だけを閉じる。閉じると起点へフォーカスを
   戻す。Tab/Shift+Tab、背景操作抑止、IME確定Enter、処理中の閉じる禁止を維持する。
   入力や暗号処理のRust所有者とコマンドは変更しない。
5. **回帰を共通境界で防ぐ。** 画面ごとのハードコード余白を追加しない。例外は用途と理由を
   記録し、共通配置契約を使う。新しいウィンドウ全体のモーダルはこの共通部品を使う。

## 追加不具合: Rooms / DMsの折りたたみ・並び替え

ユーザー報告: RoomsとDMsの両方で、折りたためず、並び替え方法を変更しても表示に反映されない。

ソース調査で共通の欠落を確認した。

1. `Shell.tsx` は `sidebar_section: { scope, section, collapsed / sort }` を送信する。
2. Rustの `SidebarSettings::apply_section_patch` はscope別・section別の設定を更新する。
3. `compose_sidebar_for_state` はその設定から並び順と折りたたみ状態を正しく投影する。
4. しかし `crates/koushi-core/src/state_delta.rs` のサイドバー再投影条件は従来の
   `room_list_sort` だけを比較し、新しい `sidebar.scope_preferences` を比較していない。
5. フロントエンドは `snapshot.sidebar.rooms_collapsed` / `dms_collapsed` とRustが並べた
   一覧を表示するため、設定だけの変更ではその表示投影が更新されない。

この欠落は両方の症状と整合する。追加のユーザー観測では、別のSpaceへ移動して戻ると
折りたたみが適用されている。Space切替は既存の再投影条件に含まれるため、設定変更だけでは
更新されなかった表示が切替時に更新される、という説明と一致する。これは実行中の設定保持を
裏付けるが、ディスクへの永続保存や再起動後の復元まで証明するものではない。
添付診断では差分の適用が継続しており、世代欠落による再取得・古い差分の無視・JSエラーは
報告されていない。セクション設定の変更値や再投影理由は記録されておらず、診断単独では
当該操作の経路を確定できない。調査時点では動的再現テストは未実施だった。
既存の設定投影単体テストとUIコマンド送信テストだけでは、差分配信の欠落を検出できない。

修正計画:

- レイアウト変更とは独立した修正単位とする。
- まずCoreの差分生成テストを新しい対象別テストファイルに追加し、他のルーム変更なしで
  Rooms / DMsの折りたたみ・並び順変更が `changed.sidebar` に出ることを要求してREDを確認する。
- ユーザー報告の「折りたたむ→即時反映しない→別Spaceへ移動→戻ると反映」を再現経路として
  記録する。修正後の合格条件はSpace移動なしで即時反映し、往復後もその状態を維持すること。
- Rustの差分生成条件に、セクション設定の依存関係を加える。React側で独自に折りたたみ状態や
  並び順を持ったり、強制リロードで補う実装にはしない。
- Home、Space A、Space Bで、RoomsとDMsの設定が独立していることを確認する。
  非表示scopeの設定変更が現在の一覧を誤って変えず、scope切替後に正しく適用されることも含む。
- ブラウザでは本番と同じ差分適用経路へRust型の結果を渡し、操作直後の `aria-expanded`、
  子一覧の表示/非表示、メニュー選択、実際の表示順が一致することを確認する。
  UI fakeだけで投影を再実装したテストをCoreの差分配信の代用にしない。
- 設定の保存・再読込を検証し、再起動後の復元を確認する。初回のscope設定作成時にも
  片方の折りたたみ操作が他方の並び順など未変更設定を変えないことを検証する。
