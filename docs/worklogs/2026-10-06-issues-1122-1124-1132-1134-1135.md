# Room mention text, save naming, typing cost, idle writes, scheduled-send time (#1122, #1124, #1132, #1134, #1135)

Five issues delivered as one batch at the maintainer's request. Each keeps the
existing layer ownership: Rust owns product state and Matrix semantics, React
renders Rust DTOs and dispatches typed commands, Tauri is transport.

## #1122 — the composer inserts `@@room`

`ROOM_MENTION_CANDIDATE.label` is `"@room"` (the text its autocomplete row
shows), while its target's `display_label` is `"room"`. `acceptMention` passes
`peopleFacingLabel(candidate.label)` as the inline label for every candidate, and
Rust renders an inline as `'@' + display_label` in both `plain_body` and
`mention_html`, so the body, the formatted body and the composer pill all carry
the doubled at-sign.

Fix: only a `roomMention` target takes its inline label from the target's own
`display_label`. The autocomplete row keeps showing `@room`, user mentions keep
the display label from the profile, and the `room` (matrix.to room link) target
keeps the previous label selection.

Evidence: a browser-headless spec that picks the ROOM NOTIFICATION suggestion,
asserts the pill text is `@room`, and asserts the dispatched `send_text` document
carries `target: { kind: "roomMention", display_label: "room" }` with
`display_label: "room"`. Plus the existing Rust body/formatted-body tests.

## #1124 — the scheduled send time could not be changed on Linux

The previous session could not reproduce a failure on the committed Linux GUI
lane: the field is a real `datetime-local`, keyboard-editable, and create, edit,
cancel and fire are green. What the lane *cannot* drive is the native picker
popup, which is a GTK UI-process window, not DOM; and the picker covers only the
date, so the time of day is reachable only by discovering keyboard segment
editing.

Rather than guess at the reporter's environment, this change makes the moment
directly editable with the mouse on every platform: explicit `-1 h`, `-10 min`,
`+10 min`, `+1 h` adjustments next to the field, in both the composer's Send-later
form and the scheduled-message edit form. The native field stays, the button only
moves the value the app already owns, and `Schedule send` still submits the same
`send_at_ms`.

Evidence: browser-headless specs that click the adjustments and assert the
submitted `schedule_send` timestamp moved by exactly the pressed delta, and the
Linux GUI lane driving the same buttons (Linux evidence token added).

## #1132 — composer typing cost on Linux

Confirmed causes from the maintainer's investigation, in the recommended order:

1. **The draft debounce loses its timer handle.** `updateComposerDraft` replaces
   the overlay (with `debounceHandle: null`) *before* `queueComposerDraftPersist`
   cancels, so cancellation always sees the new overlay and the previous timer
   survives; 20 rapid edits leave 20 live timers and produce 20 `set_composer_draft`
   commands instead of one.
   Fix: the lifecycle registry owns the pending handle.
   `clearDebounce(scope)` returns the handle it removed, so the caller clears the
   real window timer, and the overlay no longer keeps a second copy. Same fix for
   the thread composer.
2. **Every keystroke rebuilds the whole editor.** The `beforeinput` handler
   cancels the native edit, publishes a new document, and the layout effect calls
   `renderEditorDocument`, which builds new spans and calls `replaceChildren`.
   Fix: when the previously rendered document and the new document have the same
   inline shape and differ only in text payloads, update the existing text nodes
   in place instead of replacing the subtree. Structural changes (mentions,
   inline count or order, sentinel) still rebuild.

Not in this change, per the investigation's own order: the narrow composer delta
(item 3) and the mention/persistence coalescing (item 4). Both are protocol or
worker changes that the maintainer asked to decide after measuring the first two;
the worklog records the measurement method.

Evidence: a DOM spec asserting a single-character insert into a non-empty
composer keeps the original text node (today it is disconnected), and a
browser-headless spec asserting one `set_composer_draft` after N rapid edits.

## #1134 — idle disk writes dominated by the crypto store

Confirmed by source: `ClientBuilder::new` defaults to
`CrossProcessLockConfig::MultiProcess`; `EncryptionSyncService` takes the crypto
store's cross-process lock only in that mode and holds the guard for the whole
sync stream; while held, the lease is renewed every `EXTEND_LEASE_EVERY_MS = 50`
ms with a SQLite write, which never stops while idle.

Fix: declare exclusive store ownership only where it is guaranteed. The packaged
app's runtime paths (`start_with_data_dir_and_os_backend*`) call
`StoreActor::with_exclusive_store_root()`, which makes the SDK store config apply
`CrossProcessLockConfig::SingleProcess`; in that mode `try_lock_once`/`spin_lock`
are no-ops that never touch the store and `EncryptionSyncService` skips the lock
block entirely. No vendored-SDK patch. Every other entry point — QA, smoke, tests,
`KOUSHI_QA_DATA_DIR` reuse — keeps the SDK's multi-process coordination, because
those can be pointed at a store root another process already owns.

Not in this change, and not claimed: the byte-volume measurement on a real idle
session. The evidence here is the mechanism: the shipped configuration test
asserts that an exclusive store root reports `SingleProcess` and a shared root
reports `MultiProcess`, and the SDK source shows the lease renewal is the only
writer that path adds. A bound on store write transactions per minute with no
incoming events (poll the crypto WAL's modification metadata after an
initialization barrier, count changed sampling intervals, pin the runtime to one
worker) is the remaining check, and it needs the reporter's environment to be
comparable.

Investigated and not changed: `navigation.v1.enc` already persists only changed
content (`runtime/reducer_support.rs` compares the persisted view before
scheduling), and the read-state outbox waits for changed requests before its
debounce but can still save an identical snapshot because publication bumps the
save generation unconditionally (`crates/koushi-core/src/timeline/read_state.rs`).
Suppressing that at its owner is a separate, measurable change.

## #1135 — generic media names collide in the Downloads folder

`default_media_save_path` proposes `<Downloads>/<sanitized filename>`, and pasted
screenshots and most clients' image uploads are all named `image.png`, so every
save proposes the same path.

Fix: the naming policy stays in `koushi_core::media_save` and gains an explicit
kind and local timestamp. When the item is an image and its filename is a known
generic upload name (the allowlist in the issue: `image.*`, `Pasted image*`,
`clipboard*`, `screenshot.png`, or empty), the proposed name is
`Koushi_Image_<YYYYMMDD>_<HHMMSS>.<ext>` in local time; a meaningful filename is
kept, including for `m.file` attachments. The prefix is catalog-owned but
resolved through `tInvariant`, because it becomes part of a generated filename
and must not be translated or pseudo-localized; the catalog still owns the save
dialog's title.

Local time is resolved where the platform's timezone data lives: the renderer
passes the event's `origin_server_ts` and that instant's `Date` timezone offset,
and Rust does the calendar math, so the whole name remains unit-testable in Core.
The existing `saveMediaFile` transport carries the two facts; no new command and
no filesystem de-duplication (the OS save dialog already asks before
overwriting).

Evidence: Rust unit tests for every allowlist entry, for a kept meaningful name,
for extension handling and for the civil-date math across month, year and leap
boundaries.
