## #1322 — a muted room's row display count

The canon claimed a muted room's display count "uses the greater of the unread
and notification counters". The reducer has always used the raw unread sum:

- `crates/koushi-state/src/state/room.rs:436-440` — a muted row's count is
  `room.unread_count.saturating_add(room.thread_unread_count)`;
  `notification_count` is not read for that branch.
- The `max(...)` formula the old text echoed belongs to a *different* field,
  `koushi_state::room_activity_unread_count`, documented at
  `state-machine.md:2134` and `overview.md:1013`, which the room row does not
  render as its count.

`state-machine.md:1057` now names `RoomAttentionProjection.display_count` and
its real formula, so the canon agrees with the deliberate, test-pinned
behaviour. No reducer change: raw-unread-for-muted is pinned by
`crates/koushi-state/tests/thread_badge_state.rs:120-127` and
`crates/koushi-state/tests/navigation_state/sidebar_sorting.rs:119-126`.

## #1323 — diagnosing the nightly `user_verification` red

Committed as `0755ad15`. The scenario's "request sent" precondition was the
command-acceptance projection, which already reads `Requested` before the SDK
has sent anything (`runtime.rs:5729` projects it at command acceptance), so a
parked send and a delivered-but-unprojectable request produced one token.

- `wait_for_outgoing_request_sent` is one event loop requiring both A's
  room-list membership and the account actor's post-send
  `VerificationProgress { Requested, initiator: Us }` event, emitted only from
  the `Ok` branch after the real `koushi_sdk::request_user_verification`
  (`contact_security.rs:88-124`). It reports `a_send=finished|optimistic_only`
  and fails fast on a typed failure.
- The failure text gained `b_dm_room_listed_at_send` and
  `b_dm_joined_members_at_send`, plus a failure-path-only probe
  (`probe_b_dm_timeline`, 15 s bound, `unknown` on any error) reporting
  `b_dm_timeline=undecryptable|no_undecryptable_item|unknown`.
- `docs/agents/qa-lanes.md` drops the false ordering claim, records the omitted
  tokens, and documents the open gap.

Root cause, read out of the vendored SDK rather than inferred: the only entry
point that hands an in-room verification event to the crypto verification
machine sits inside the `Decrypted(..)` arm of
`matrix-sdk-base/src/response_processors/e2ee/decrypt.rs:45-53`. A first pass
returning `UnableToDecrypt` yields a UTD, the event never reaches the machine,
and nothing replays it for verification — the redecryptor and the room APIs
re-decrypt for display only, and no public `matrix-sdk` API re-feeds an in-room
verification event. Whether the room key or the event wins is a coin flip
because `koushi-core/src/sync.rs:1-8` splits Sliding Sync into an `all_rooms`
list connection and a separate `encryption` connection, so the to-device megolm
share and the room event are two independent long-polls. Measured margins: red
key `11.551752Z` against the responder's UTD `11.534763Z` (-17 ms); green key
`36.056487Z` against the request processed `36.072212Z` (+16 ms).

Observed red on the shipped build (`/tmp/uv-final/r1/run-mbrJox`, EXIT=1,
97.5 s; the pre-probe repro was 97.2 s, so the probe adds no time):

```text
... a_send=finished a_room_list_joined_members=2 b_dm_room_listed_at_send=true
b_dm_joined_members_at_send=2 b_dm_timeline=no_undecryptable_item b_flow=idle
b_target_matched=false b_sync=running
```

The probe's own answer is evidence: 90 s after the sync-time UTD the
responder's timeline holds no undecryptable item, so the request is eventually
visible to the responder while the verification machine never saw it. The probe
itself was validated on a forced-failure scratch build (2/2 reds,
sub-millisecond, then reverted and confirmed byte-identical).

Refused, and recorded as refused: a vendored-SDK fork change, reaching into SDK
internals, and masking the flake through a longer timeout, a scenario retry, or
DM seeding. A "wait for the responder's room list before sending" gate was
written and then reverted on evidence: the one red run already satisfied that
gate's own condition, while the gate removed a real interleaving.

## #1326 — a headless proof of the OAuth/MAS sign-in path

New files:

- `crates/koushi-core-testkit/tests/support/oauth_fixture.rs` serves a real
  authorization server and homeserver over TCP on `127.0.0.1:0`. PKCE S256 is
  verified for real, and the observation log records method and path only.
- `crates/koushi-core-testkit/tests/oauth_authorization_code.rs` holds the 13
  tests: no code, no state, or neither never reaches the token endpoint; a
  mismatched state is rejected; the code exchange installs a persistent session
  that survives a restart and reuse; a rejected exchange is a typed, redacted
  failure; an unverified device is admitted but not promoted to `LoggedIn`.
- `.github/workflows/ci.yml` gains the proof step inside the required `rust`
  job.
- `scripts/check-leaf-crate-boundaries.mjs` gains the new target in its
  `testkitTargets` registry, which is otherwise a hard CI failure.

Two root causes are worth recording because neither was obvious:

- The fixture's first failure was a 404, not a product defect. The SDK requests
  `/_matrix/client/unstable/org.matrix.msc2965/auth_metadata` unless the client
  advertises Matrix 1.15, so serving only the `/v1/` path is not enough:
  `ruma-client-api/src/discovery/get_authorization_server_metadata.rs:30-31`.
- A test held `CoreConnection` across `runtime.shutdown().await`. AppActor stops
  only once every command sender is dropped and the connection owns one, so
  shutdown waited forever; the repo convention is
  `drop(connection); runtime.shutdown().await;` (`runtime_session.rs:459`). The
  symptom was a process parked on `_pthread_cond_wait` with the fixture idle in
  `__accept`, indistinguishable from a slow test unless the stack is sampled.

The proof also surfaced a production wart, corrected here.
`classify_oauth_error` mapped every `OAuthError::AuthorizationCode(_)` to an
HTTP-response transport, so a callback that never left the machine was reported
as a server rejection with a null status. `Cancelled`, `InvalidState` and
`RedirectUri(_)` are now local; `RequestToken` still classifies its real
response, and the catch-all is kept because the error enum is
`#[non_exhaustive]`. Being precise about the effect: both consumers map the old
and the new value to the same coarse failure kind, so the typed detail changed,
not what the user is told.

The workspace gate earned its place in this run: it was the only red job, and it
was red for a reason no focused run could show. `--workspace` unifies features

session ready. That runtime restores its session from disk and reports ready
before the restored client reaches the network, so the assertion was a race:
eight runs in ten failed under synthetic CPU load. It now waits, bounded, for the
request, counting only requests the restarted runtime itself made; expiring the
wait still fails the proof. Ten runs in ten pass under that same load. A gate
that is green only on an idle machine is not green.
